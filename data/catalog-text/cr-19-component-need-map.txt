Translate the page into a table of needs before choosing a single component. Read the reference screen and list every action and readout it carries, then write two columns, need and component, resolving each need to one entry of a fixed vocabulary: the one main action on a screen becomes a primary button at 40 or 48 px, any other action a secondary at 32 or 40, a quiet action that owns no box until hovered a ghost, anything that deletes or cannot be undone a filled danger button, one of a few choices a segmented control at 32 px with a sliding selection, one of many a dropdown whose rows are 32 px, a value to type a 40 px field with a real label, a status word a fully round pill, a name and its value a two-column stat row rather than a sentence, and nothing yet an empty state carrying one next action. Cap the plan at one primary per screen and one danger per destructive flow, and forbid a destructive control within 64 px of a primary one. Order the rows as the build order: shell, navigation, main action, fields, list and rows, status, empty and error. Each row names its states before it is coded, rest, hover, focus-visible, pressed, disabled, plus open or loading where they apply. Acceptance: every interactive element in the build maps to a row; no row goes unused; no screen shows two primary buttons; every row lists its states before implementation; the destructive distance rule holds; the table alone is enough for a second developer to start the build.
